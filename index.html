01Project Overview

태산자전거 S/4HANA ERP 구축 프로젝트 · MM 모듈 담당

표준 테이블을 쓰지 않고 전 모듈을 CBO 테이블로 새로 설계·구현하는 Full-Custom 프로젝트에서 MM(자재관리) 모듈을 담당했습니다. 테이블·데이터 요소 정의부터 화면, 비즈니스 로직, 타 모듈 인터페이스까지 구매 업무의 처음과 끝을 직접 만들었습니다.

가장 신경 쓴 것은 데이터 정합성입니다. 확정 시점 단가의 고정 저장, 송장 단위 Roll-up 검증, "1송장 = 1 FI전표" 원자성 보장처럼, 화면 뒤에서 데이터가 어긋나지 않게 하는 설계에 시간을 썼습니다.

산출물 : ABAP 프로그램 5종 + Fiori(UI5) 앱 3종, 프로그램 스펙서, 단위/통합 테스트

04Troubleshooting

개발 중 실제로 부딪히고 해결한 문제들 — 문제 · 해결 · 배운 점

FI 전표 부분 전기로 인한 MM-FI 정합성 붕괴 송장검증

문제

대량 전기 중 일부 오류 발생 시 이미 처리된 송장만 전기되어 MM 이력과 FI 전표 건수가 불일치. 원인은 FI 함수 내부의 COMMIT WORK로 트랜잭션 경계가 분산된 것.

해결

함수는 예외(RAISE)만 발생시키고 커밋을 금지하도록 FI 담당과 스펙을 문서로 합의. 호출자가 최상위에서 단일 COMMIT WORK AND WAIT / 오류 시 ROLLBACK 수행 → "1송장 = 1전표" 원자성 보장.

배움

모듈 간 인터페이스는 코드보다 트랜잭션(LUW) 경계 합의가 먼저다.

ALV 이벤트 핸들러 내 오류 메시지로 프로그램 강제 종료 자재마스터

문제

셀 편집 검증에서 MESSAGE TYPE 'E' 출력 시 프로그램이 비정상 종료되고 입력 데이터 유실. ALV 이벤트 핸들러는 PAI 흐름 밖에서 동작하기 때문.

해결

TYPE 'S' DISPLAY LIKE 'E'로 전환해 흐름을 유지하고, 검증 실패는 플래그로 저장 로직을 차단. 셀 검증은 data_changed_finished 이벤트로 이관.

배움

프레임워크의 이벤트 실행 컨텍스트를 이해해야 문법상 정상인 코드의 런타임 오류를 막을 수 있다.

저장 시 미관리 필드가 공백으로 덮어써지는 데이터 유실 자재마스터 · PIR

문제

화면에 없는 필드가 저장 시 초기값(공백)으로 DB를 덮어써 다른 프로그램의 조회가 깨짐.

해결

저장 패턴 표준화 — DB 원본을 먼저 적재(ls_save = ls_db)한 뒤 화면 값만 MOVE-CORRESPONDING으로 덮어쓰고 MODIFY. 변경 행만 선별 반영.

배움

"화면 = 테이블 전체"라는 가정은 위험하다. 이후 모든 저장 로직에 원본 우선 적재 패턴을 적용했다.

RAP 채번 시점에 일반 필드 세팅 불가 QR 관리 (RAP)

문제

QR 번호 채번을 earlynumbering_create에서 처리하며 발행일시·발행자도 함께 세팅했으나 키 외 필드가 저장되지 않음. 스펙상 키 필드만 반환 가능.

해결

책임 분리 — 채번은 earlynumbering에서 키만, 일반 필드는 별도 Determination(on save)으로 이관. 재발행 로직도 같은 구조로 분리해 중복 발행 차단.

배움

클래식 ABAP 습관대로 한 곳에서 처리하지 말고, RAP 프레임워크의 단계별 역할에 맞춰 설계해야 한다.
